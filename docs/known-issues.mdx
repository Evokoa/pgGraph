# Known Issues

<Callout type="warning">
pgGraph is currently alpha software. Do not use it for production workloads
without your own validation, backup, rollback, and load-testing plan.
</Callout>

<Callout type="info">
pgGraph is built around a simple launch standard: the most critical correctness,
durability, safety, and operational paths should be solid first. There is always
another way to optimize a graph engine, especially inside PostgreSQL, so we are
tracking gaps in those paths explicitly and continuously hardening them in the
open before recommending production use.
</Callout>

This page documents known alpha limitations, next-update hardening work, and
lower-priority follow-up items. The list is ranked by expected user impact, not
by implementation difficulty.

This page is the authoritative register for known limitations and correctness,
operational, performance, or maintainability risks. Future product direction,
new APIs, and feature expansion belong in [Roadmap](./roadmap). Completed
hardening work remains documented in historical release notes and the resolved
summaries below.

Low-level PostgreSQL extension work involves real tradeoffs. Some optimizations
make a query faster by keeping more data in memory, while others reduce memory
pressure by doing more work per request. pgGraph has to weigh those choices
carefully because it runs inside PostgreSQL backend processes rather than a
separate service with its own resource envelope.

## P0: Correctness, Security, Durability, and Resource Bounds

These are the highest-priority public follow-ups because they affect operators
running larger graphs or higher sync volume, and because some findings can
change observable graph correctness or PostgreSQL security boundaries.

`graph.memory_profile()` remains useful for capacity planning, but visibility is
not enforcement. `graph.memory_limit_mb` is not a cluster-wide hard cap, and
important build, load, query, and maintenance allocations are not yet governed
by one byte budget.

| ID | Issue | Status | Notes |
|---|---|---|---|
| KI-012 | Build resource accounting does not yet bound PostgreSQL temporary-file and server-side executor memory. | P0 architecture fix | Checked preflight and live Rust reservations now cover stale positive estimates, long keys, filters, resolution, both CSR directions, relationship identity, and persistence buffers. Adaptive byte batches and fallible major-vector growth fail with `PG001`. PostgreSQL temporary storage, allocator/RSS calibration, and out-of-core construction remain before retirement. |
| KI-013 | mmap load, GQL/path execution, sync, projection reads, compaction, and analytics can allocate outside the build guard. | P0 architecture fix | Persist/mmap inbound CSR and large filter metadata; add query work/byte breakers, lazy scans/neighbor merges, bounded hydration and blocking operators, pinned projection snapshots, and range compaction. |
| KI-018 | Persisted replacement is renamed over the serving path before mmap reload validation. | P0 durability fix | Write and validate a generation-specific artifact, catch it up, then atomically switch a small manifest while retaining the previous generation. |

## Roadmap-Owned Future Work

Do not use this known-issues register for broad feature wishes that are not
current limitations. Track these in [Roadmap](./roadmap) instead:

- complete ISO GQL syntax and semantics beyond the current subset;
- costed multi-pattern planning, streaming execution, relationship property
  expressions, and optional path-variable projection semantics;
- a dedicated many-to-many relationship registration helper if post-fix user
  reports show `graph.add_edge()` remains too easy to misuse;
- PostgreSQL 19 SQL/PGQ catalog and `GRAPH_TABLE` interoperation;
- broader openCypher compatibility;
- semantic-guided search and pgVector ranking;
- WAL-driven sync;
- COPY build scanning;
- additional graph analytics;
- distributed graph execution.

## Lower-Priority Optimizations

These are intentionally deferred until measurement shows they matter:

- Replacing bitmap serialized-size estimates with native roaring helpers if the
  pinned crate exposes them.
- Reducing low-level clone counts in builder, traversal, weighted path, and
  aggregation paths.
- Combining duplicate path reconstruction passes after the larger traversal
  allocation work is complete.
- Cleaning up long internal function signatures when the surrounding traversal
  parameters stabilize.
- Cleaning up padding-bit handling in `active_count()`.

Canonical enums/newtypes, native UUID/OID boundaries, checked conversions, and
unsafe proof are active correctness work, not benchmark-dependent
micro-optimizations.
